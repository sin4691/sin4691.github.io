모바일 공장 게임

2026.08 – 09 · 4인 팀 · Android

시뮬레이션과 화면을 분리해, 모바일 터치 환경에서 벨트 물류가 안정적으로 돌아가게 했습니다.

개요
벨트와 기계로 자원을 운반·가공하는 싱글 플레이 모바일 공장 게임
내 역할
벨트 물류 시뮬레이션(순수 C# SimulationWorld) · 기계 처리 · 모바일 건설 UX(벨트 드래그, 기계 배치, 영역 철거, 터치 카메라) · PlayMode 테스트 약 50개 · 프리팹 배리언트 생성과 Addressables 등록을 자동화하는 에디터 도구
팀원 담당
기계·레시피 데이터(Machines.json 등)와 광고 연동. 제 코드는 그 데이터를 읽어서 사용합니다.
기술
Unity, C#, Addressables, Input System, NUnit, Android 빌드
링크
GitHubAPK

구조

입력·건설 도구 → SimulationWorld(순수 C#) → 렌더링 순서로 나눴습니다. 시뮬레이션이 MonoBehaviour가 아니라서 씬 없이 테스트할 수 있고, 누적기 방식의 고정 틱으로 구동해 프레임이 흔들려도 결과가 같습니다. 벨트 위 아이템은 GameObject가 아니라 struct 리스트이며, "추월 불가" 규칙만으로 뒤가 막히면 압축되는 역압(back-pressure)이 만들어집니다.

트러블슈팅

1벨트를 앞에 이어 붙이면 아이템이 멈춰 보이는 버그

문제
리스트 순서가 곧 "하류→상류" 처리 순서라고 가정했습니다. 그런데 기존 벨트 앞쪽에 새 세그먼트를 이으면 리스트 뒤에 붙지만 실제로는 상류입니다. 경계에서 한 틱씩 낡은 상태로 판단해 아이템이 멈춘 것처럼 보였습니다.
해결
배열 순서를 믿지 않고 NextSegmentId를 따라 후위 순회 DFS로 매 틱 처리 순서를 다시 계산해 하류부터 처리합니다. 상류·하류를 일부러 반대 순서로 넘겨 재현하는 회귀 테스트(Tick_ProcessesDownstreamFirst_EvenWhenArrayOrderIsUpstreamFirst)로 고정했습니다.
// BeltSystemTests.cs 발췌 — 회귀 테스트
var downstream = new BeltSegment { Id = 0, Length = 1f, SpeedUnitsPerSecond = 5f };
var upstream   = new BeltSegment { Id = 1, Length = 1f, SpeedUnitsPerSecond = 5f, NextSegmentId = 0 };
upstream.Items.Add(new BeltItem(0, 0.9f));
var segments = new List<BeltSegment> { downstream, upstream };   // 상류가 리스트 뒤
for (int i = 0; i < 20; i++) system.Tick(0.05f, segments, processors, null);

Assert.AreEqual(0, upstream.Items.Count);         // 상류에서 하류로 넘어갔어야 함
Assert.AreEqual(1, downstream.Items.Count);
Assert.Greater(downstream.Items[0].Position, 0f); // 제자리에 멈추면 안 됨

2정체(clog)와, 철거하면 환불이 두 배가 되는 버그

문제
① 구리가 벨트를 막아 철판이 지나가지 못했습니다. ② 미니 코어가 메인 코어의 입출력 버퍼 배열을 참조로 공유하는데, 철거 시 그 배열이 두 번 환불돼 자원이 두 배가 됐습니다.
해결
① 라인별 담당 자원을 고정(lane locking)했습니다. ② 버퍼가 코어와 같은 배열인지 ReferenceEquals로 판정해 공유 버퍼는 환불에서 제외하고, 인덱스가 밀리지 않도록 삭제는 List.RemoveAt 대신 null 슬롯(톰스톤)으로 처리했습니다.

3손가락에 가려지지 않는 모바일 건설 조작

문제
터치 개수에 따라 건설과 카메라 조작을 나눠야 하는데, 두 번째 손가락이 닿는 순간 진행 중이던 건설 제스처가 남으면 오작동합니다. 기계를 손가락 바로 아래에 보여주면 손에 가려지고, 손을 떼는 순간 확정하면 오조작하기 쉽습니다.
해결
BuildInputRouter가 1터치는 건설, 2터치는 카메라로 나누고 2터치가 시작되면 진행 중인 건설을 취소합니다. 카메라는 해상도와 관계없이 손가락 1:1 드래그가 되도록 계산했습니다. 기계는 반투명 고스트(MachineGhostTool)를 손가락 위로 화면 오프셋 150px만큼 띄우고, 확인 버튼을 눌러야 배치되며 유효(초록)/무효(빨강)로 미리 칠합니다.

한계와 개선 계획

  • 시각 오브젝트를 GameObject.Find 이름 검색으로 찾는 부분은 세그먼트 ID 딕셔너리로 바꿀 예정입니다.
  • 월드 그리드 일부 조회가 O(N) 스캔이고 레인 점유 판정이 O(N²)라서 역방향 인덱스와 캐싱으로 줄일 예정입니다.
  • 프로파일러 실측 수치(FPS·GC·메모리)는 9월 29일 프로젝트 종료 후 실기기 기준으로 추가합니다.

트러블슈팅

1난이도 의견 충돌을 플레이 테스트로 풀기

문제
난이도를 두고 팀 의견이 갈렸습니다. 저는 낮춰야 한다고 봤고, "지금도 낮다"는 의견과 중립도 있었습니다. 이 게임은 협동·트롤·퍼즐·컨트롤이 한꺼번에 있고, 실수하면 뒤로 가는 구조라 피로도가 높습니다.
접근
서로 겹치지 않는 약 40명(제가 진행한 20명, 팀원 약 12명, 같은 교육과정의 다른 두 팀 8명)에게 플레이 테스트를 받았습니다. 게임을 많이 해 본 사람은 엔딩을 2시간 안에 봤지만, 일반 플레이어는 챕터 2까지만 약 2시간이 걸렸고 챕터 3 초반에서 "너무 지친다"며 종료했습니다. 타깃은 게임을 아주 잘하는 4명이 아니라 협동 게임을 좋아하는 일반 4명이고, 협동 게임은 한 명이 그만두면 4명이 함께 이탈·환불할 수 있다는 점을 논거로 삼았습니다.
결과
메인 챕터는 낮은 난이도로 두고, 엔딩 뒤에 도전하는 매우 어려운 Ex 스테이지(Ex 1~2)를 추가하기로 팀이 합의했습니다. 엔딩 직후 또는 커맨드 키로 진입합니다. Ex 1~2 맵을 제작했고 체크포인트 없는 버전의 씬도 설정했습니다. 의견 차이는 성향이 아니라 어떤 플레이어를 기준으로 봤는가에서 나온 것이어서, 쉬운 메인과 어려운 선택 콘텐츠로 서로의 요구를 나눠 담았습니다.

2서버 권위 자동 스크롤 보스 (BossChase)

문제
보스가 뒤에서 쫓아오는 구간에서 서버는 각 클라이언트의 카메라를 알 수 없습니다. 뒤처진 플레이어를 방치하면 팀이 멈추고, 보스가 너무 가까우면 억울하게 죽습니다.
접근
이동은 서버에서만 계산하고, "가장 뒤처진 플레이어와의 X 거리 14 이내"를 화면 안으로 근사했습니다. 화면 안 2 · 화면 밖(따라잡기) 6 · 누구든 3 이내로 가까우면 1로 속도를 바꾸고, 전환은 MoveTowards로 부드럽게 했습니다.
결과
협동 압박은 유지하면서 뒤처진 사람 때문에 게임이 멈추지 않고, 근접 감속으로 억울한 즉사를 줄이는 난이도 조절 장치가 됐습니다. 한계도 있습니다. X축 거리만 쓰기 때문에 세로로 긴 맵에는 맞지 않습니다.
// BossChase.cs 발췌 (Mirror, 서버에서만 실행)
[ServerCallback]
void FixedUpdate()
{
    float targetSpeed;
    if (IsAnyPlayerTooClose()) targetSpeed = slowSpeed;                 // 1
    else targetSpeed = IsOnScreen() ? normalSpeed : catchUpSpeed;       // 2 / 6

    currentSpeed = Mathf.MoveTowards(currentSpeed, targetSpeed,

}

3플레이어가 하얗게 나오는 네트워크 버그 (팀원 코드 수정)

문제
서버가 플레이어에게 색상 번호를 배정하는데, 연결이 끊긴 "유령" connectionId가 번호를 계속 쥐고 있어 빈 번호가 없으면 -1이 배정됐고, 플레이어가 하얗게 표시됐습니다.
해결
번호를 배정하기 전에 NetworkServer.connections와 대조해 죽은 ID를 정리하고, 그래도 빈 번호가 없으면 connId % 4로 대체했습니다. 씬 전환 중인 접속은 번호를 보존하고 실제 퇴장일 때만 회수합니다. 이 스크립트(CoopPlayerIdentity)의 원 작성자는 팀원이며, 저는 버그 수정으로 기여했습니다.

3로비 강화 UI를 이벤트로 갱신하기

문제
로비에는 강화 카드 6종(체력·공격·대시·골드·부활·이동속도)이 있고, 구매하면 카드의 레벨·비용·버튼 상태가 함께 바뀌어야 합니다. 카드가 매 프레임 값을 물어보면 낭비이고, 구매한 카드만 갱신하면 화면이 어긋납니다.
해결
LobbyManager가 강화 적용이 끝날 때 OnUpgradeChanged 이벤트를 발생시키고, 각 UpgradeCardUI가 구독해 자기 카드를 다시 그립니다. 구독은 OnEnable, 해제는 OnDisable에 짝지어 패널을 껐다 켜도 중복 등록되지 않게 했습니다.
// UpgradeCardUI.cs 발췌
private void OnEnable()
{
    buyButton.onClick.AddListener(OnBuyClicked);
    if (LobbyManager.Instance != null)
    {
        LobbyManager.Instance.OnUpgradeChanged += Refresh;   // 구독
        Refresh();
    }
}
private void OnDisable()
{
    buyButton.onClick.RemoveListener(OnBuyClicked);
    if (LobbyManager.Instance != null)
        LobbyManager.Instance.OnUpgradeChanged -= Refresh;   // 해제
}

회고

  • 강화 비용·보너스 배열이 LobbyManager와 PlayerData.ResetRunData에 중복되어 있고, 기본 이동속도도 5와 7.5로 어긋나 있습니다. 단일 출처(ScriptableObject)로 완전히 옮기지 못한 것이 아쉽습니다.
  • PR 템플릿과 CI가 없었고, 빌드 zip·발표 자료 같은 대용량 파일이 저장소에 들어갔습니다. 다음에는 Releases와 Git LFS, .gitignore를 처음부터 정하겠습니다.

핵심 구현

1"보이면 쫓아오는" 대신 "소리를 내면 쫓아오는" 은신 시스템

문제
공포 게임에서 시야 감지 AI는 플레이어에게 선택지를 주지 않습니다. 은신, 그리고 위험과 보상의 선택이 있는 구조를 만들고 싶었습니다.
접근
플레이어의 이동 상태(달리기 · 걷기 · 앉아서 걷기 · 정지)마다 다른 소음 반경(15 · 6 · 2 · 0)을 부여했고, 몬스터는 플레이어와의 거리가 현재 소음 반경 안에 들어오면 발각한 것으로 판단합니다.
결과
조용히 지나갈지, 달려서 빨리 끝낼지가 플레이 판단이 됩니다.
// PlayerMovement.cs — 이동 상태로 소음 반경 결정
if (isMoving && isRunning)          noiseRadius = 15f;  // 달리기
else if (isMoving && isCrouching)   noiseRadius = 2f;   // 앉아서 이동
else if (isMoving)                  noiseRadius = 6f;   // 걷기
else                                noiseRadius = 0f;   // 정지

2AI 추격 상태 머신

소리로 발각되면 그 위치를 실시간으로 계속 갱신하고, 몬스터가 최신 발각 위치까지 이동하도록 구현했습니다. 감지한 즉시 달려들지 않고 1초간 비명을 낸 뒤 추격해서 플레이어에게 도망칠 시간을 줍니다. 도착 후에는 주변을 둘러보는 Idle 상태(4초)로 전환해 재탐색하고, 플레이어를 놓쳤을 때도 자연스럽게 순찰로 이어집니다. NavMesh에 없는 위치의 소리에는 Blocked 상태로 전환해 무한 탐색에 빠지지 않습니다.

트러블슈팅

1상태 재진입, 1인칭 머리 가림, 벽 밀착 투척

문제
① 같은 상태로 다시 들어가면 코루틴이 재시작되어 로직이 중복됐습니다. ② 1인칭 카메라를 눈 위치에 두면 자기 머리 메시가 화면을 가렸습니다. ③ 벽에 붙거나 앉은 채 아이템을 던지면 물리 충돌로 맵 밖으로 사라졌습니다.
해결
① 상태 변경 함수에 if (state == next) return; 가드를 두었습니다. ② 스켈레톤의 Neck 본을 찾아 런타임에 스케일을 없앴습니다(HideHead). ③ Raycast로 투척 지점을 먼저 계산하고 검증된 hit.point에서 생성합니다.

2절차적 던전 위에 NavMesh 얹기

문제
DunGen이 실행 중에 던전을 생성하므로 미리 구운 NavMesh를 쓸 수 없고, 몬스터도 생성이 끝나기 전에는 길을 찾을 수 없습니다.
해결
DungeonNavMesh가 DunGen의 생성 완료 이벤트를 받아 NavMeshSurface를 한 프레임 뒤 다시 굽도록 했습니다. 다만 ItemSpawner는 이벤트 대신 고정 2초를 기다리는데, 기기 성능에 따라 실패할 수 있어 같은 방식으로 바꿔야 합니다.

3한 달 일정에 맞춰 범위 줄이기

문제
초기 기획에는 시드 기반 랜덤 스폰, 손전등, 문 열기, NavMesh 적이 모두 있었지만 일정은 한 달이었습니다.
해결
문 열기 시스템을 취소하고, 몬스터 랜덤 스폰 대신 맵 끝 방에 고정 배치했습니다. 줄인 자리에 시간을 몰아 몬스터 AI·애니메이션, 아이템 스폰, 플레이어 상호작용, 타이머·게임 루프를 끝까지 완성했습니다.

회고 — AI 도구를 쓴 방식과 대가

에셋 사용법 학습, 버그 원인 추적, 리팩토링 검토에 AI 도구를 썼습니다. 다만 에셋(설정 패널)을 AI의 도움으로 통합하면서 내부 구조를 끝까지 파악하지 못해, 발표 시점에 메인 메뉴와 인게임 설정 패널의 스위치 표시가 반대인 버그를 고치지 못했습니다. AI에게 코드를 맡길 수는 있어도 이해를 맡길 수는 없고, 그 코드의 책임도 개발자에게 있다는 것을 배웠습니다.

  • 몬스터의 소리 감지가 직선 거리 기준이라 벽 너머의 소리도 듣습니다. NavMesh 경로 거리나 벽 감쇠를 반영해야 합니다.
  • 몬스터는 1종이고, 사망 시 씬 리로드(체크포인트 없음)이며, 다중 몬스터 배치와 문 열기는 미완성으로 남겼습니다.
